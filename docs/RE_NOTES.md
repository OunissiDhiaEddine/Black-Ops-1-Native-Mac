## Float model (SSE2 vs x87)
Source: `tools/float_census.py` -> `re/float_census.json`. Method: capstone 5.0.7 **linear sweep** of `.text` (5,904,912 B) — 1,848,603 instructions decoded, only 116 undecodable bytes; inline data is mis-decoded as code, so counts are good to a few percent. | Class | Instructions | Share of FP |
|---|---|---|
| SSE scalar single (`movss/addss/mulss/comiss…`) | 157,768 | 61.0% |
| x87 | 71,419 | 27.6% |
| SSE packed single | 24,833 | 9.6% |
| SSE scalar double | 3,375 | 1.3% |
| SSE packed double | 1,331 | 0.5% |
| SIMD integer (SSE2) / MMX / SSSE3 / SSE3 | 15,736 / 4,172 / 1,080 / 253 | — |

- **Mixed model, SSE-dominant.** The compiler targeted SSE scalar math (`/arch:SSE`-style) but x87 is everywhere at ABI edges: `fld`+`fstp` are 70% of all x87 instructions (float return values in ST(0), float<->memory moves). Real x87 arithmetic is ~12k instructions (`fmul/fadd/fsub/fdiv`), plus `fsincos`/`fsin`/`fyl2x`/`fsqrt` (statically linked CRT math) and 254 `fldcw` (float->int truncation idiom).
- Lifter consequence: x87 support is mandatory (stack model + ST(0) return convention) but can start as a `double`-precision stack; 80-bit precision only matters if diff tests show divergence. No AVX. SSSE3/SSE3 present in small numbers (LIKELY CPU-dispatched codec paths; 12 `cpuid`).
- **x87 precision control (T-042).** `CreateDevice` is called without `D3DCREATE_FPU_PRESERVE` (CONFIRMED, D3D9 census), so on Windows Direct3D switches the calling thread's FCW to 24-bit precision; every x87 result on that thread is rounded to `float` from then on. The lifter models this (`x87_pc` in `src/runtime/lifted_fp.h`, exercised by the diff tests with FCW 0x07F); the runtime's `CreateDevice` shim must clear FCW bits 8-9 on the calling guest thread (TODO T-045). Whether game logic depends on it: GUESS (unknown).
- **Lifter census (T-042, exact, per function — supersedes the linear-sweep estimate for "what must be supported"):** 217 distinct unsupported mnemonics after the integer subset; all but ~10 instructions are now lifted. MMX is real (8.4k `movq`, `psadbw`, `paddw`… in ~100 functions — LIKELY a statically linked video/codec path); SSSE3 `palignr` appears in 2 functions only (CPU-dispatched; our CPUID reports no SSSE3).
- 2,534 aligned XMM memory accesses (`movaps/movdqa [mem]`) -> guest stack/heap alignment must be preserved (16-byte).

## Frame structure of a mission frame (khe_sanh frame 5200, from the replay's pass dump — T-056)
Source: `BO1_DEBUG_FRAME=5200 BO1_DEBUG_DIR=artifacts/debug/khe_sanh_5200 build/replay artifacts/traces/khe_sanh.bin --backend metal --frames 5199-5200`, then `tools/pass_dump.py`. CONFIRMED for that frame (2,984 draws, 29 passes); names of the effects are my reading of the images (LIKELY).
1. **Float-Z pre-pass** — colour = R32F 800x600 ("float Z"), depth = the main D24FS8. `Clear(target|z|stencil, 0xFFFFFFFF, 1.0)`, then ONE full-screen quad (z test off) whose pixel shader writes the constant **2,000,000.0** — the "far" value a D3DCOLOR clear cannot express — then ~950 draws writing view depth (values seen: 1 … 6,161).
   - The quad's vertices come from a small static vertex buffer (stride 32, position = float4 in pixels, mapped by c0–c3 = `x*2/W-1`, `1-y*2/H`) that the game fills **once, in frame 1, with a DISCARD lock**. CONFIRMED (only lock of that buffer in the whole trace).
2. **Depth-only pass** — colour = FOURCC `NULL` target, same depth buffer, ~950 draws (LIKELY the depth pre-pass proper).
3. **Scene** — back buffer, ~950 draws (lit world, sky) + 45 blended draws (decals / effects).
4. `StretchRect` back buffer -> a full-size A8R8G8B8 texture ("resolved scene"), repeated after each of the following stages.
5. **Soft particles / dust** — 72 blended draws; two of the four pixel shaders sample float Z at `vPos * c5.zw` and fade with `saturate((|floatZ| - particleDepth) * c6.x) * vertexAlpha`. Where float Z is wrong the dust disappears.
6. **Downsample chain** — A16B16G16R16 400x300 -> 200x150 -> 100x75 (several ping-pong passes; LIKELY bloom / exposure), one A8R8G8B8 100x75.
7. Two full-screen passes on the back buffer (LIKELY bloom composite and colour grading), then a **depth-of-field** chain: three 200x150 A8R8G8B8 blurs and a final full-screen composite.
- Depth is attached to passes whose colour target is smaller than it (200x150 colour with the 800x600 depth buffer): legal in D3D9; Metal accepts it in practice (no validation error seen in the replay so far — not checked with the debug layer for this frame; GUESS that it stays harmless).

## The Direct3D calls of a frame and the render thread (P6 / T-063 — census + profiles of the native build, 2026-10-10)
- **Call mix** — CONFIRMED (`re/d3d9_census_cuba.json`, 3,405,715 draws). Per `DrawIndexedPrimitive` the game makes: 1.06 `SetTexture`, 1.00 `SetPixelShaderConstantF` (always ONE register), 0.84 `SetVertexShaderConstantF` (4, 3 or 1 registers), 0.72 `SetStreamSource`, 0.58 `SetSamplerState`, 0.44 index-buffer `Lock` + `Unlock` (the dynamic index buffer, `NOOVERWRITE`), 0.41 `SetIndices`, 0.19 `SetRenderState`, 0.19 `SetPixelShader`, 0.17 `SetVertexShader`, 0.15 `SetVertexDeclaration`. So a frame is ~6 calls per draw, and nearly every draw changes a texture and both constant blocks; the game does its own filtering of repeated state (few render-state calls), which is why most of what reaches the device is a real change.
- **Scenes used for measuring** — CONFIRMED (`artifacts/boot/p6_final.log`): the user's checkpoint saves `cuba-1` (street fight) = ~30,800 calls per frame, `cuba-2` = ~15,600; the main menu's room = ~13,300 (what is on screen between the title key and the first load; the T-058 runs counted the same there).
- **Who makes the calls** — CONFIRMED (`artifacts/boot/p6_after2_sample1.txt`: every device call lies under it): the engine thread started through `Sys_ThreadMain` (0x0082FDE0) that runs 0x006EBE00 (`R_InitThenPresent_caller` in `re/symbols.csv`; it is the render thread's function). Chain to the device, by sample counts: 0x006EBE00 -> 0x006EBAE0 -> 0x006EB760 -> 0x006D2EC0 -> 0x006D2100 -> {0x00737ED0, 0x00738500, 0x00738730, 0x007382E0} -> 0x00726850 -> … -> 0x006E6B00 -> 0x006E66F0 -> {0x0073E7B0, 0x0073E020} -> 0x00749010 / 0x00748B40 / 0x00748EC0 / 0x00749450 / 0x00749810 / 0x00749510 / 0x007496C0, which call the device.
  - GUESS (from position in the chain and call counts only, not read in the disassembly): 0x006D2100 runs one render pass's command list (four callers = pass kinds), 0x006E66F0 is the per-surface loop, 0x0073E7B0 sets a material pass up (textures, samplers, constants), 0x0073E020 issues the draw. To be read before T-064 touches them.
  - 0x006E66F0 read (T-064, 2026-10-10) — CONFIRMED from its disassembly, correcting the guess above: it is not the per-surface loop but "draw one run of surfaces that share a material". `edi` = a small iterator (`[0]` = render context, `[4]` = state, `[8]` = index of the current surface, `[0xC]` -> {array of 8-byte sort keys, count}). It reads the current 64-bit key, takes the surface type from bits 19–22 of the high dword, calls 0x0073FD90 (selects the material's technique; 0 = nothing to draw), then for each of the technique's passes (`u16` count at `[technique+6]`): 0x007279E0 (pass state), and an indirect call through the table at 0x00B4AEE8 indexed by surface type — those table functions are the per-surface loops and each returns how far it got. The fixed-point block in the middle (`fsincos` on a time value at `[context+0x1A3C]`) refreshes a cached sin / cos pair once per frame. ## Scene culling: box against a plane set (T-064 — read in the disassembly, 2026-10-12)
- 0x0071FBC0 — CONFIRMED (disassembly; `src/native/scene_cull.c` reproduces it, `scripts/test_native.sh` compares the result with the lifted original): `eax` = plane set, `esi` = the box's floats; returns 1 in `eax` when the box is outside one plane. A plane set holds up to 16 entries of 20 bytes — `float nx, ny, nz, dist`, then three bytes that are the byte offsets, into the box, of the x, y and z to test (the corner farthest along the normal, chosen when the set is built) — and its count as `u32` at +0x140. Test per plane: `((x*nx + dist) + y*ny) + z*nz <= 0` culls; a NaN does not. Its only caller is 0x00721530 (two sites: the boxes are 40 bytes apart in the array at `[[0x0460C0AC]+0x54]` and 80 bytes apart, +0x38, in the one at `+0x58`), which then calls 0x0071FC30 (not read; SIMD, 2,052 bytes) for the boxes that pass.
- LIKELY (from the profiles only): 0x00720440 (4,333 bytes, 457 SIMD instructions, no calls) is the bulk form of the same culling; 0x008F2950 / 0x008F2B00 are the worker threads' job-queue polling loops — they dominate the lifted self-time of a quiet scene (`cuba-2`), i.e. that time is waiting, not work.

## CPU skinning of model vertices (T-064 — read in the disassembly, 2026-10-10)
- **What the four functions are** — CONFIRMED (disassembly; `src/native/skin_verts.c` reproduces them and `scripts/test_native.sh` compares every output byte with the lifted originals): the model-vertex skinning loops, one per number of bones a vertex is weighted to. 0x00744790 calls them in turn (1, 2, 3, 4 bones) with the four vertex counts it reads as `u16` at `[info+0..6]`; the blend data of a surface is one stream, the 1-bone entries first. 0x00745280, the job the worker threads run, walks a list of surfaces and brackets the loops with `emms` (LIKELY: read only that far). A second family with more arguments (0x00746190, 0x00746390, 0x00746630, 0x00746980, called from 0x00744860) was not read and is not in the profile.
- **Arguments** — CONFIRMED: 1 and 2 bones: `eax` = vertex count, `edx` = blend data, stack = source vertices, bone matrices, destination, `int *` vertex index. 3 and 4 bones: `eax` = destination, bone matrices in `edi` (3) / `esi` (4), stack = source, blend data, count, `int *` index. The index is where to start in both vertex arrays and is advanced by the count; a count <= 0 does nothing. All four are caller-cleans.
- **Vertex (32 bytes, same layout in and out)** — CONFIRMED: `float x, y, z, w` · 8 bytes copied unchanged (LIKELY colour + texture coordinate) · packed normal (4 bytes) · packed tangent (4 bytes). Of `w` only the sign is used: the output's fourth float is `+1.0` or `-1.0` (masks at 0x00B5FF30 / 0x00B5FF40) — LIKELY the handedness of the tangent frame.
- **Blend data** (`u16` each) — CONFIRMED: 1 bone: byte offset of the bone matrix. 2 bones: offset A, offset B, weight of B. 3: offset A, offset B, weight B, offset C, weight C. 4: one more (offset, weight) pair. Weights are fractions of 65536 (0x00B455A0 = 1/65536); bone A gets `1 - the others` (0x00B45570 = 1.0). A bone matrix is 64 bytes, four rows of four floats, at `matrices + offset`.
- **Arithmetic** — CONFIRMED: position = `(x*r0 + y*r1) + (z*r2 + r3)` per bone, then for 2 bones `wB*(pB - pA) + pA`, for 3 `(pC*wC + pB*wB) + pA*((1 - wB) - wC)`, for 4 `(pD*wD + (pC*wC + pB*wB)) + pA*(((1 - wB) - wC) - wD)`. Normal and tangent use the FIRST bone only: bytes -> float, `n = (b - (127,127,127,-192)) / (127,127,127,255)`, `t = n * n.w`, rotate `(t.x*r0 + t.y*r1) + t.z*r2`, fourth lane replaced by `r3.w`, times the scale plus the bias again, `cvtps2pi` (round to nearest) and three `packuswb`. The association of the additions matters for bit-equality and is as written.
- **Cost** — CONFIRMED for this machine (`scripts/test_native.sh --bench`, one process, best of 5, under other load): the lifted loops take 450–860 ns per vertex (1 to 4 bones), the native ones 8–16 ns. The lifted code is slow here because every MMX / SSE register lives in memory and every float -> integer conversion goes through `rint()` on a double.

## Bink as the game uses it (T-054 / ADR-008) — from the game's own code
Source: `tools/bink_sites.py` (listing of the game's cinematic code 0x006D8000–0x006DA2C0 with every `binkw32.dll` call named; `--sites` = the 30 import sites). Everything below was read from the game's instructions at the VAs given; the field NAMES are those of RAD's public `bink.h` and are LIKELY (the offsets and what the game does with them are CONFIRMED). No code of `binkw32.dll` was looked at.

**`BINK` (the handle `BinkOpen` returns, kept at 0x03E4CA80) — the game reads only four fields:**
| Offset | Field | Read at | Use |
|---|---|---|---|
| +0x08 | `Frames` | 0x006D9249, 0x006D9348, 0x006D9361, 0x006D9F52 | last frame when `FrameNum == Frames` -> movie finished (unless looping, flag 2) |
| +0x0C | `FrameNum` (1-based) | 0x006D908F, 0x006D922E, 0x006D924E (`== 1` -> restart the game's own clock), 0x006D8FEF, 0x006D9F55 | current frame |
| +0x14 | `FrameRate` | 0x006D98B2, 0x006D9F68 | fps = `FrameRate / FrameRateDiv` (float at 0x03E4CA68) |
| +0x18 | `FrameRateDiv` | 0x006D98C2, 0x006D9F6D (**integer `div`** — must not be 0) | |
Width / Height (+0, +4) are never read from the handle: the picture size comes from `BINKFRAMEBUFFERS`.

**`BINKFRAMEBUFFERS` (global at 0x03E4CA84, 0x78 bytes; the game clears 0xD8 bytes there, the rest is its own texture table):**
| Offset | Field | Who writes | Notes |
|---|---|---|---|
| +0x00 | `TotalFrames` | Bink (`BinkGetFrameBuffersInfo`) | loop bound at 0x006D9137; the game's own tables hold 2 sets |
| +0x04 / +0x08 | `YABufferWidth` / `YABufferHeight` | Bink | Y and A texture size and plane size (`w*h` bytes, 0x006D89C9) |
| +0x0C / +0x10 | `cRcBBufferWidth` / `cRcBBufferHeight` | Bink | chroma texture and plane size |
| +0x14 | `FrameNum` | Bink (`BinkDoFrame`) | which frame set was just decoded; read at 0x006D9328 and by the upload (0x006D8D58) |
| +0x18 + i*0x30 | `Frames[i]`: four `BINKPLANE {Allocate, Buffer, BufferPitch}` in the order Y, cR, cB, A | `Allocate` by Bink; `Buffer` / `BufferPitch` by the game | A plane exists iff `Frames[i].APlane.Allocate != 0` (0x006D88E6) |
- Order of calls at start (0x006D9C2C–0x006D9C6D): `BinkGetFrameBuffersInfo(bink, fb)` -> the game creates L8 textures and allocates plane memory -> `BinkRegisterFrameBuffers(bink, fb)`.
- **Before every `BinkDoFrame`** the game rewrites `Buffer` and `BufferPitch` of all planes of all sets in that same block (0x006D9150–0x006D91AD; pitch = buffer width). So the decoder must keep the POINTER given to `BinkRegisterFrameBuffers` and read the planes from it at decode time, not copy the struct — CONFIRMED on the game side, LIKELY for what the original DLL does.
- After `BinkDoFrame` the game copies `Frames[fb.FrameNum]` planes row by row into the locked textures (0x006D8D50: `LockRect` with `D3DLOCK_DISCARD`, source pitch = buffer width) — on a worker command or directly, depending on the thread.
- The trace shows what Bink reports for the shipped 1280x720 files: Y 1280x720, chroma 640x360 (RE_NOTES "D3D9 census": DYNAMIC L8 textures) — CONFIRMED for the texture sizes, so `YABuffer* = 1280x720`, `cRcBBuffer* = 640x360`.

**`BINKREALTIME` (`BinkGetRealtime(bink, &rt, 0)`), fields read:** +0x00 `FrameNum`, +0x04 `FrameRate`, +0x08 `FrameRateDiv` -> position in ms = `FrameNum * FrameRateDiv * 1000 / FrameRate` (64-bit helpers, 0x006D93AB–0x006D93F1; **`FrameRate` must not be 0**, it is a divisor; the value is only computed when `FrameNum < 0x80000000`); +0x2C `ReadBufferSize`, +0x30 `ReadBufferUsed` -> buffer fill in percent (0x006D8CD0: 100 when `Used >= Size`).
- The fill percentage drives behaviour: after `BinkOpen` the game waits until it is >= 10 (0x006D9829, while background I/O is on); during playback < 20 pauses the movie ("buffering", 0x006D9033), > 95 stops background I/O and < 50 restarts it (0x006D9410 / 0x006D9438). A decoder that reads whole frames itself should report `Used == Size` (100%).

**Calls and arguments (all stdcall; `re/import_abi.csv`):**
- `BinkSetMemory(0x006D9610, 0x006D9640)` — the game's own bump allocator; a host decoder does not need it.
- `BinkSetSoundSystem(BinkOpenDirectSound, <IDirectSound* at 0x03B370CC>)` only if that pointer is non-NULL; `BinkSetSoundTrack(5, {0,1,2,3,4})`; after open `BinkSetVolume(bink, track, vol)` x5: tracks 0 and 1 at the cinematic volume (0..0x8000), tracks 2–4 at 0.
- `BinkOpen(path, 0x01104400)` for files (`BinkSetIOSize(arena - 0x180000)` first) and `BinkOpen(memory, 0x04104400)` for a rawfile from the fastfile (`bik/<name>.bik`, flag 8). Flag names per the public header (LIKELY): `BINKIOSIZE | BINKALPHA | BINKSNDTRACK | BINKNOFRAMEBUFFERS`, and `BINKFROMMEMORY` instead of `BINKIOSIZE`. Paths: `<base>\main\video\<name>.bik`, then `<base>\raw\video\<name>.bik`; on failure the default movie is tried ("R_Cinematic_BinkOpen '%s' failed: %s; trying default.").
- Right after a successful file open: `BinkPause(bink, 1)`, `BinkControlBackgroundIO(bink, 2)`, wait for the buffer, `BinkPause(bink, 0)`, then loop `while (BinkWait(bink)) Sleep(1)`.
- Per update (0x006D9000, called through a pointer): `BinkGetRealtime`; `BinkPause` on state change; `BinkWait` (non-zero = not time yet; up to 33 sleeps of 1 ms in one mode) or the game's own clock (0x006D8FA0); `BinkDoFrame`; then `while (BinkShouldSkip(bink) && FrameNum != Frames) { BinkNextFrame; BinkDoFrame; }`; upload; `BinkNextFrame` unless on the last frame; `BinkGetRealtime` again for the position.

**Verified by running it natively (2026-10-06, `src/platform/win32/bink_ffmpeg.cpp`, logs `artifacts/boot/bink_run.log`, `bink_cuba_run.log`):**

## XAudio2 as the game uses it (T-053 / ADR-009) — from the game's own code and from native runs
Sources: the sound driver code at 0x008AF000–0x008B3400 and its helpers (listing with `tools/bink_sites.py --range`), `re/com_steam_usage.json` (the two `CoCreateInstance` sites), and the call counts of a native run (`tools/xaudio2_usage.py` -> `re/xaudio2_usage.csv`). Implementation: `src/platform/win32/xaudio2_faudio.cpp`.

- **Interface layout = XAudio2 2.7 SDK header, CONFIRMED at the game's call sites:** `Initialize` slot 5 with 3 stack words (0x004AACBE, 0x008B1837), `GetDeviceCount` 3 / `GetDeviceDetails` 4 (0x008B1876, 0x008B18AC; the game's buffer for the details is 0x42C bytes, `Role` read at +0x400 and compared with 0xF), `CreateSourceVoice` slot 8 with 8 words (0x008B1679), `CreateSubmixVoice` slot 9 with 8 (0x004D0DA4), `CreateMasteringVoice` slot 10 with 7 = the 2.7 form with a device index (0x008B0F9A), voice `GetVoiceDetails` slot 0 writing 12 bytes (0x008B0FC5 -> 0x0330B74C: flags, channels, rate — no `ActiveFlags`), `SetEffectParameters` slot 6 with 5 (0x004E6E56), `SetOutputMatrix` slot 16 with 6 (0x008B116A, 0x004D0E0B), `DestroyVoice` slot 18, `SubmitSourceBuffer` slot 21 with 3 (0x008B16CB), `StopEngine` slot 12 (0x008B11FD).
- **Start-up** (0x00436820 -> 0x008B19D0 -> 0x008B0F40): a first XAudio2 object only enumerates devices (up to 16; each is tried with a mastering voice that is destroyed again) and is released; the real one (pointer at 0x0330B318) gets a mastering voice (0x0330B748; `InputSampleRate` = 48000 only if the device reports more than 48000, else 0 = "device rate") and three submix voices, each with ONE effect: 2 ch stage 3 (effect object 0x0330B780, voice 0x0330B758), 2 ch stage 2 (0x03317500, voice 0x033174E0), 4 ch stage 1 (0x03322E80, voice 0x03322E1C).
- **Every effect is the game's own code** (XAPO objects in the image; none of the XAudio2FX / XAPOFX class ids occurs in the exe — byte search). They answer `QueryInterface` for IID_IXAPO {A90BC001-E897-E897-55E4-9E4700000000} (bytes at 0x005BEE40) and IID_IXAPOParameters {…0001} (0x005AA858) — the 2.7 ids. Every source voice is created with one such effect as well (effect chain of 1 at 0x008B165D) and two sends.
- **The effects assume a 48 kHz engine** — CONFIRMED the hard way: with a 44.1 kHz output device the engine ran 441-frame blocks, and an effect's `Process` (0x004B93C0 -> … -> 0x005F370D) wrote past its internal buffer over the game's variables at 0x03322E1C (the stage-1 submix voice pointer), which crashed the next sound update (0x004E6E45). Whether real XAudio2 2.7 would behave differently at 44.1 kHz is unknown (GUESS: it processes each voice's effects at the voice's own rate, FAudio after resampling). The port therefore always runs the mastering voice at 48000 Hz and lets SDL convert for the device.
- **Sound formats seen:** MS-ADPCM and PCM (decoded by FAudio) and **xWMA** (`wFormatTag` 0x161, 2 ch, 48000 Hz, block 4096, no extra bytes; `SubmitSourceBuffer` then passes an `XAUDIO2_BUFFER_WMA` packet table — the `[edi+0x2C]` test at 0x008B16AF). Homebrew's FAudio has no WMA decoder (it would call a null function), so xWMA voices are created as 16-bit PCM and each buffer is decoded with FFmpeg's `wmav2` first; the decoded length is taken from the last entry of the packet table. This is what the Wine baseline could NOT do ("GStreamer doesn't support WMA" x260 in the baseline log) — those sounds were silent there.
- **Calls in a 170 s run from start-up into mission 1** (`re/xaudio2_usage.csv`, 19 of 83 methods): per frame `SetOutputMatrix` (276,642), `GetState` (183,770), `SetEffectParameters` (138,321 on source voices, 27,147 on the submixes) and `SetFrequencyRatio` (137,993); 516 source voices created, 483 destroyed, 998 buffers submitted, 647 `Start`, 483 `Stop`. Not called at all: `RegisterForCallbacks`, `SetVolume`, filters, `FlushSourceBuffers`, `ExitLoop`, `CommitChanges` (every call uses operation set 0).
- **Threads:** callbacks into game code (voice callbacks, effect `Process` / `SetParameters`) run on a mixer thread of the runtime that has guest state (`thread_spawn_host`); the audio device's own thread only hands each 10 ms block over. Effect sample buffers are copied through guest memory (the effect is guest code, the engine's buffers are host memory).
- **DirectSound** (`DirectSoundCreate8` at 0x0090EC9C) is still answered with "no driver": the game only uses it to hand Bink a sound device and for voice chat ("[play] failed to initialize DirectSound", "R_Cinematic_Init: Unable to initialize sound" are still printed and harmless). The movies' sound does not need it in the port: `bink_ffmpeg.cpp` decodes the sound tracks itself and plays them on the game's XAudio2 engine through host-side stream voices (`xaudio2_stream_*` in `xaudio2_faudio.cpp`).
- **Movie sound tracks** (ffprobe + native run): track ids are in the file — `treyarch.bik` has 0 (stereo) and 3 (stereo), `cuba_load.bik` 0 (stereo), 1 (mono), 3 (stereo), all `binkaudio_dct` 48 kHz; the menu movie has none. The game's five `BinkSetVolume` calls play ids 0 and 1 at the cinematic volume (23167 / 32768 = 0.707 at full) and mute 2–4 — CONFIRMED in the captured mix: intro peak 0.63 against 0.89 in the file = 0.707. LIKELY meaning: 0 = front left/right, 1 = centre, 3 = surround pair for 5.1 set-ups.

## Mouse as the game uses it (T-057) — from the game's own code
Source: the three cursor call sites (`tools/bink_sites.py --range 008677D0 00867930`, `--range 005B7700 005B7701`). CONFIRMED by reading; the fix was confirmed by the user's hand only for keyboard so far.
- **No raw input, no DirectInput:** the mouse is `GetCursorPos` once per frame (0x0086785D, the only site; 204,955 calls in the baseline runs) inside 0x00867840, and only while `GetForegroundWindow()` is the game's window (handle at 0x027706BC).
- **Movement = current position − previous position** (previous at 0x0276C0B8 / 0x0276C0BC), handed with the client position to 0x0041EE50. When that returns non-zero (the game wants the mouse for looking) and the cursor moved, 0x005B7700 **puts the cursor back in the centre of the window with `SetCursorPos`** and records the centre as the previous position.
- Consequence for a port: `SetCursorPos` must really move the cursor the game reads. As a no-op (the runtime until 2026-10-06) the next frame reports the full offset from the centre again — every frame — so the view turns at a rate proportional to how far the pointer is from the window centre. That is what the user described as trackpad "acceleration".
- Other `SetCursorPos` users: 0x008677D0 clamps the cursor into the window rectangle (only when the byte at `[0x03B1FA24]+0x18` is set), 0x00491740 places it at a client position (menus). `ShowCursor` is called in a loop until the counter is where the game wants it (0x00867910).
- The runtime's answer (`WindowService::warp`, `win_messages.cpp`): a virtual cursor that `SetCursorPos` places and relative mouse motion moves; SDL relative mouse mode (pointer hidden and held) while the game keeps re-centring, released 500 ms after the last call or when the window loses focus.

## Saves, disconnect and display restart as the game does them (T-061 / T-060) — from the game's own code and native runs
- **End of a mission (T-070)** — from the disassembly, CONFIRMED by a native run for the `changelevel` path. The script builtin `changelevel` (0x007FBBB0) copies the next map's name to 0x01C018B0 (64 bytes, through 0x0049B530), may set a delay at 0x01C07020 and sets the request at 0x01C07014; `missionsuccess` (0x007FBCD0) does the same and sets 0x01C07018. The server frame (0x0045A6C0) calls 0x0041DE40 every frame: a request goes to 0x007E30B0, which — only if the player is alive and `[0x01C0186C]+0x18` is 0 — sets the exit time 0x01C0700C = level time + delay + 1000 ms; when that time has come, the plain path (0x00510690) queues `spmap <name>` (`spdevmap` with `sv_cheats`; `disconnect` when the name is empty), and the missionsuccess path queues `cinematic <name> 0` if 0x01C07024 holds a movie name, otherwise sends the client the server command `1` (0x31). Native run: the plain path loads the next mission (`artifacts/boot/m2_changelevel.log`). The missionsuccess path: the client's command dispatcher (0x0078DAF0, a switch on the command's first character; found through its text "Unknown client game command") sends `1` to 0x004715B0, which opens the UI menu number 9, `victoryscreen` (0x005852C0 -> 0x0055B510). CONFIRMED natively (`artifacts/boot/m2_trace2.log`): that menu does not exist while a mission is loaded — the open returns 0 — and the mission simply goes on. The console command `nextlevel` (0x0083B060, a jump to 0x00510690) would then load the stored map (`m2_missionsuccess2.log`), but nothing issues it.
- **What the game's own script does at the end of a campaign mission** — CONFIRMED from the script text (it is zlib-compressed inside the already inflated `code_post_gfx.ff`; `maps\_endmission`): `nextmission()` -> `_nextmission()` updates the profile and achievements, then calls `ChangeLevel(next, keepWeapons)` when the level was registered with `skip_success`, else `MissionSuccess(...)`. Every campaign level is registered with `skip_success = true`, so the campaign only ever takes the plain path. The level list also shows what follows what: cuba -> **so_narrative1_frontend** -> vorkuta -> pentagon -> flashpoint -> so_narrative2_frontend -> khe_sanh -> hue_city -> kowloon -> so_narrative3_frontend -> fullahead -> creek_1 -> so_narrative4_frontend -> river -> wmd_sr71 -> wmd -> pow -> so_narrative5_frontend -> rebirth -> int_escape -> underwaterbase -> outro. The interludes are maps of their own (the interrogation room; they load the `frontend` fastfiles) whose script ends with `ChangeLevel(GetDvar("ui_load_level"))`. Native run (`m2_narrative.log`): cuba -> the request for so_narrative1_frontend -> its loading movie, start save, the room with its screens and subtitles -> the interlude itself queues `spdevmap vorkuta` -> vorkuta loads and starts.
Read with `tools/xref.py` (string / address references, direct callers, plain disassembly) and `tools/bink_sites.py --range`.
- **Save files** are `players\save\<name>.svg` (`save/%s.svg`); a save is written to `save\temp.svg` and then stored under its name (CONFIRMED: `CreateFileA` order in every native run). Header (first 0x24 bytes, from the three files at hand): `+0x00` 0x134, `+0x0C` a small counter, `+0x20` the map name. LIKELY (only compared, not traced).
- **There is no console command that saves.** `savegame` is a script builtin (0x007FAD20, entry `{name, handler}` in the table at 0x00B76A14) and the menu scripts `Savegame` / `forcesave` (dispatcher 0x00420240) save under the name in the dvar at 0x02598F0C. All of them queue a request with 0x0043C850 (up to 3 pending, 0x19C bytes each at 0x02899800, count at 0x02899CD4; refused while `g_reloading` is set — "savegame request ignored" — or within 3,000 ms of the previous one) and 0x004BC500 writes the queue. CONFIRMED (code); typing `savegame x` in the console does nothing (run 1).
- **Level-start save:** 0x0087E150 queues "Start Level Save" when a map starts (`sv_saveOnStartMap`); the file is `<map>.svg`. CONFIRMED (written ~1 s after `CL_InitCGame` in every `devmap cuba`).
- **Console commands that load:** `loadgame <name>`, `loadgame_continue` (registered in 0x0057DBE0), `savegame_commit` / `savegame_lastcommit` (0x004FD1F0). `loadgame cuba` works from inside the mission and from the menu (CONFIRMED natively: "Save game build number: 152", "=== G_LoadGame ===", the scene restarts from its opening).
- **After a save named `internal/vid_restart` (or `internal/snd_restart`) has been written,** 0x0087DFF0 queues `disconnect;vid_restart;loadgame internal/vid_restart` — the game's way of restarting the renderer in the middle of a mission. CONFIRMED (code); who queues that save was not traced (LIKELY a script reacting to the options menu).
- **`disconnect` is a non-local jump.** It raises `Com_Error` "PLATFORM_DISCONNECTED_FROM_SERVER", and `Com_Error` leaves through the CRT's `longjmp` (0x0096B980, ends in `jmp [buf+0x14]`) to the last `_setjmp3` (0x00969EAC) of the thread: the buffer is `Sys_GetValue(2)`, set once per frame in 0x00636A30 (return address 0x00636A60) and in `Com_Init` (0x004069D5, 0x00406A11, 0x00406A91). 13 call sites of `_setjmp3` in the image (`re/lift_coverage.json` -> `setjmp_call_sites`). CONFIRMED natively: before the lifter knew about it the run stopped with "indirect target is not a function at 00636a60"; now the game prints "Disconnecting: Disconnected from server", shuts the server down and loads the menu map. So quitting a mission, and every dropped error, depends on this path.
- **`vid_restart`** (handler 0x005B52A0, registered at 0x00591608) acts only while a game or the menu map is running (bit 0x20 of 0x0291015C, set in `CL_InitCGame`) and only if one of seven renderer dvars has a pending value (0x006B7D60; `r_mode` is one of them — "r_mode will be changed upon restarting."). It then sets the request flag 0x03963478 and waits in `Sleep(5)` until the render thread has served it. CONFIRMED (code + runs 3 and 6: without a changed dvar nothing happens).
- **Dropped errors recover; the fatal-error routine is 0x004C9B60 (`Sys_Error`).** `devmap nosuchmap` -> "Com_ERROR: Couldn't find the bsp for this map" -> the same `longjmp` -> error screen at the menu; Escape returns to the menu map and loading works again (CONFIRMED natively, `t061_error_run10.log`). `Sys_Error` enters critical section 0xD, sets 0x024817B0, suspends every other thread (0x0056C440, the only `SuspendThread` site), formats the message, restores the desktop mode (0x00601DF0 -> `ChangeDisplaySettingsA(NULL)`, then `EnumThreadWindows`), shows the error dialog (0x005ACC60) with its own message loop and exits. "Cannot unload world while it is in use" is ORIGINAL behaviour (CONFIRMED 2026-10-07 in the Wine reference: `devmap <missing map>`, then `devmap cuba` 20 s later with the error screen still up -> the same message box from the same call chain, `artifacts/baseline/d3d9_census-20261007-074318.txt`). Natively it was seen when a load was scripted while the error screen was still up (called from 0x0060BEF0 <- 0x007A3C90 <- 0x00631B10; lldb back-trace). `EnumThreadWindows` has no shim yet, so a fatal error still ends in "unimplemented import" before its text is shown — read the text with lldb: break on `f_004c9b60`, the format string is at guest `[esp+4]`.
- **The real window follows the Direct3D mode, not the game's window calls.** In full screen the game only does `SetWindowPos(hwnd, HWND_TOPMOST, …, SWP_NOSIZE | SWP_NOMOVE)`, so size and full-screen state are taken from the `D3DPRESENT_PARAMETERS` of `CreateDevice` / `Reset` (`BackBufferWidth` / `Height`, `Windowed` at +32) in `d3d9_live.cpp` and handed to `WindowService::set_display`. Design, not yet tried in a window (2026-10-07).
- **The restart is a device `Reset`, not a new device.** The render thread's present function (0x006EB1F0) sees the flag, skips `Present`, treats the frame as `D3DERR_DEVICELOST`, calls `TestCooperativeLevel`, releases what it must (0x006B88C0, 0x006B70C0) and runs 0x006B89C0 "Recovering lost device...": 0x006B86C0 "R_ResetDevice()..." fills the present parameters (0x006B67B0), calls `IDirect3DDevice9::Reset`, then `SetWindowPos` (windowed: the outer size for the new client area, flags 0x62; full screen: topmost, no move / size) and re-creates render targets, buffers and queries; then "R_ReloadWorld()...", "R_ReloadLostImages()...", "Finished recovering lost device.". CONFIRMED natively at the menu and inside cuba (800x600 -> 1024x768 -> 800x600). The same path would serve a really lost device; the shim never reports one.

## Native runtime — what the first full boot taught (2026-10-06)
- **Host pages are 16 KiB, guest pages 4 KiB.** The game decommits hunk memory right up to a page it keeps (`VirtualFree(MEM_DECOMMIT)` from 0x0047D114); anything that re-maps host pages must not touch a host page that is only partly inside the range. CONFIRMED (the lost animation-type names -> "BG_IndexForString: unknown token 'm203'").
- **Message pump** (main thread): `PeekMessageA(PM_NOREMOVE)` then `GetMessageA`, `TranslateMessage`, `DispatchMessageA`; the render thread also calls `PeekMessageA`. CONFIRMED (import log).
- **FS_Startup** resolves its base path with `GetFullPathNameA("C:.")` (0x0096CCD6): drive-relative paths must work. CONFIRMED.
- **Missing subsystems are tolerated at start-up:** XAudio2 creation failing -> "failed to initialize DirectSound", `BinkOpen` failing -> the movie is skipped ("trying default … not playing movie"). CONFIRMED for the title screen, the menu and the start of cuba.
- **The game's debug output is a precise oracle:** up to the first runtime bug the native boot printed the same 670 debug strings as the Wine baseline (differences only in paths, CPU name, video memory, host name).
- **Direct3D object ids and lifetime (T-059):** the renderer keys everything by the guest address of the COM object, and since T-059 those addresses are reused: `d3d9_null.cpp` destroys an object when its last reference is gone **and** the device no longer has it bound, frees its guest memory (object, lock memory, a texture's level table and level objects) and reports the destruction to the renderer through `d3d9_set_destroy_hook` (the game's own `Release` calls are no longer forwarded). Rules implemented, as in Direct3D 9: a texture level's `AddRef` / `Release` count on its texture (LIKELY — from the Wine d3d9 test suite's "texture and surface refcount are identical", not measured on Windows); bound textures, stream sources, indices, shaders, declaration, render targets and depth-stencil are held by the device; back buffer, automatic depth-stencil and swap chain belong to the device; the device holds its `IDirect3D9`. Not implemented: the device reference each resource holds in Direct3D (the game's own device `AddRef` / `Release` are balanced: 123 / 123 in the menu census). In the renderer, cached pipelines go when one of their shaders or their declaration is destroyed — their cache key contains those ids.
- **`Reset`** (first called by the game in T-061, see "Saves, disconnect and display restart" above): the shim drops all bindings, resizes the implicit surfaces in place and always succeeds; the renderer gets the call with the `D3DPRESENT_PARAMETERS` blob and re-creates its back buffer with default state. CONFIRMED natively: mode changes at the menu and inside cuba render correctly afterwards, 0 uses of a dead object. Destruction of the device is still unexercised (the game keeps one device for the whole run).

## Gotchas / surprises
- **Unclean-exit marker:** the game creates `%LOCALAPPDATA%\Activision\CoD\__BlackOps` while running; if it exists at startup a modal "Run In Safe Mode?" box appears (CONFIRMED: window title seen, file found). `run_baseline.sh` deletes it; the port's file shim will see the same create/delete pattern.
- **`+devmap` on the command line is ignored, the same command through the console buffer works.** `Cbuf_AddText(0, "devmap cuba\n")` (VA 0x0049B930, called from the proxy 10 s after the title screen) loads `common` + `cuba` and starts the mission (CONFIRMED: `Loading fastfile 'cuba'`, in-game frame in `tests/golden/`). This is the baseline's scripted way into any SP map and a ready-made test hook for the port.
- **Hardware-change dialog:** "Set Optimal Settings? — Your computer appears to have changed…" (`MB_YESNO|MB_ICONQUESTION`) appears whenever the config checksum changes (CONFIRMED via MessageBoxA hook). Under Wine the measured CPU speed is garbage (`sys_configureGHz "0.00233321"`, GPU detected as "NVIDIA GeForce 6800", `sys_sysMB 1024`), so the checksum is unstable. The port must give the hardware-detection code sane, stable answers (rdtsc/QPC, GetAdapterIdentifier, memory size).
- **`config.cfg` beats the command line:** `players/config.cfg` (written on first run) overrides `+set r_fullscreen 0`; `r_mode "1280x720"` was ignored and the device came up 800x600 windowed — GUESS: the mode is validated against `EnumAdapterModes`.
- Engine threads are created with `stackSize=0` (PE default 1 MiB) and `CREATE_SUSPENDED`; two helper threads use 64 KiB stacks (CONFIRMED, CreateThread hook). The guest thread shim must honour these sizes.
- One 300 MiB `VirtualAlloc(MEM_COMMIT)` at startup (0x006122F0) — the main arena; the guest allocator must be able to commit that contiguously.
- **Reference copy is a CODEX scene release, not a Steam install — CONFIRMED** (2026-10-05; read `steam_emu.ini`: CODEX banner, `UserName=CODEX`, `[Crack]` section with 5 key=value pairs, `DLCUnlockall=1`; `~Common Redist/aio_installer.bat` is repack tooling). Consequences: hashes will not match the Steam depot; `steam_api.dll` is an emulator, so its exports/behaviour are not Valve's; `BlackOps.exe` may carry third-party patches (LIKELY — same 2016-12-25 mtime as the emulator files; not yet diffed against anything). Whether this copy stays the project reference is an open question for the user (LOG STATE).
- `BlackOps.exe` contains the strings `Valve Corp.0` / `Valve Corp.1` (`strings -a | grep`), i.e. an Authenticode certificate naming Valve is embedded — GUESS: retail exe was Valve-signed; signature validity not checked (T-004).
- No `BlackOpsMP.exe` in this install (installscript.vdf references one). Fine for ADR-001 (SP first).
